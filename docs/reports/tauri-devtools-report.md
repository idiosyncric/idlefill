## What changed

1. **`tauri/src-tauri/Cargo.toml`** — new
   `[target.'cfg(debug_assertions)'.dependencies]` block:
   `tauri-plugin-pilot = "0.8"` (resolved 0.8.1) and
   `tauri-plugin-mcp-bridge = "0.13"` (resolved 0.13.0). Cargo warns
   (`Found 'debug_assertions' in target.'cfg(...)'.dependencies ... not
   supported`) — cargo's target cfg never selects on `debug_assertions`, so
   the *deps* compile in every profile; the RUNTIME gate is the `#[cfg]`
   below (this is exactly the vendor's documented pattern; the task brief
   prescribes the block).
2. **`tauri/src-tauri/src/lib.rs`** — the builder chain is now
   `let mut builder = ...` and the vendor block registers both plugins
   inside `#[cfg(debug_assertions)]`:
   `tauri_plugin_pilot::init()` +
   `tauri_plugin_mcp_bridge::Builder::new().bind_address("127.0.0.1").build()`
   (the bridge's default bind is 0.0.0.0 — pinned to loopback). In release
   builds neither plugin is ever constructed: verified `strings
   target/release/idlefill-app | grep -ci 'tauri-pilot|mcp-bridge'` = 1
   (the inert capability-ACL strings from `generate_context!`) vs 11 in the
   debug binary — no pilot socket server, no bridge WebSocket server in the
   shipped code path.
3. **`tauri/src-tauri/capabilities/default.json`** — added `"pilot:default"`
   and `"mcp-bridge:default"` to the `shell-windows` capability. Identifiers
   verified against the crates' shipped `permissions/default.toml` (pilot:
   `allow-eval-callbacks` for `callback`/`__callback`; mcp-bridge: 13
   command perms) — not guessed. Without `pilot:default` the pilot CLI dies
   with `eval timed out after 10s`.
4. **`.agents/skills/idlefill-tauri/SKILL.md`** — repo skill (agentskills.io
   frontmatter: name/description<=60/version/author/license/platforms) with
   When-to-Use / Prerequisites / Gates / Dev-tool usage / Fences / Pitfalls.
5. **`.pi/mcp.json`** — repo-local pi MCP config wiring
   `npx -y @hypothesi/tauri-mcp-server` (stdio bridge for the in-app plugin).
6. **`AGENTS.md`** — one bullet under Commands: the tauri gates + the
   pointer to the repo skill.

## Live acceptance pass — what the owner needs to do

The pilot/MCP servers exist ONLY in debug builds. The installed
`com.sam.idlefill.app` runs the release bundle, so:

1. Rebuild with the plugins in a debug profile, e.g.
   `cd tauri && cargo-tauri tauri build --debug` (or `cargo tauri dev`)
   from this branch, and run that binary (a scratch-label path or a direct
   launch — the acceptance-test.sh hooks cover the headless variant).
2. `tauri-pilot ping` (CLI: `cargo install tauri-pilot-cli`,
   `~/.cargo/bin/tauri-pilot`) — auto-discovers
   `/tmp/tauri-pilot-com.sam.idlefill.app.sock`. Expect a version line with
   plugin 0.8.1 = CLI 0.8.1.
3. Then `snapshot -i` / `click @eN` / `eval` against the settings and
   glance windows. NOTE: the MAIN window is the remote arbiter origin —
   tauri-pilot's bridge can only drive origins listed in a capability's
   `remote.urls`; we deliberately keep NO remote block (D4-shape lock), so
   the pilot drives the bundled views only. That is the security posture,
   not a bug.
4. `tauri-pilot ping` against the INSTALLED app is EXPECTED TO FAIL
   (release build, no pilot server). Same for the MCP bridge: the
   hypothesi MCP server (`npx -y @hypothesi/tauri-mcp-server`) connects to
   the bridge's WebSocket only in debug builds.
5. Kill stale `target/debug` instances before pinging: the first debug
   instance to start owns the socket, and the CLI would drive the stale one.
