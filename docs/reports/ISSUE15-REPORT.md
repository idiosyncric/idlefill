## What changed

### `adapters/career-ops/mcp-tools-registry.mjs` (new)
The discovery + merge layer, dependency-free:

- `MODULE_API = 1` (settled decision #5), exported.
- `discoverToolModules({ repoRoot, extraPaths, coreNames })`:
  - Origin (a): one bounded scan `adapters/<dir>/idlefill-mcp-tools.mjs`
    against the same `REPO_ROOT` the server already resolves for adapter
    discovery; the optional `idlefill.mcp_tools` manifest field names a
    different file (relative to the adapter dir).
  - Origin (b): `IDLEFILL_MCP_TOOLS` (`:`-separated, absolute-or-relative).
    A path may be a module file or a directory holding the default filename
    (directory form is what makes "remove the file → gone from the list" work
    without breaking startup).
  - Validation per module: default export `{ api?, tools, call }`; missing
    `api` = 0; `api > MODULE_API` → actionable refusal naming both versions;
    import failure, empty tools, non-function call → startup error.
  - Duplicate tool name WITHIN one origin → error naming both paths. A module
    re-declaring a CORE tool name → startup error (no silent overwrite).
  - (a) shadows (b) on name collision (shadow report returned; the server
    prints it to stderr). Merged list sorted by tool name — deterministic,
    independent of readdir order.
- `register(api)` shape deliberately NOT implemented (out of scope, noted).

### `adapters/career-ops/idlefill-mcp.mjs`
- Imports the registry; startup moved into `main()`: discovery runs BEFORE
  serving; any discovery failure → message on stderr + `process.exit(1)`.
- Merged table helpers (`allToolDefs/allToolNames/toolDef/knownTool/
  isWriteTool`) replace the raw `TOOLS`/`TOOL_IMPL`/`WRITE_TOOLS` lookups in
  the #14 policy path (`visibleToolsFor`, `enforceToolPolicy`,
  `shapeToolForList`, `unionToolsForList`, `tools/list`, `tools/call`) — so
  `tools/list` = `(core ∪ discovered) ∩ policy`, flowing THROUGH the existing
  policy filter, not around it.
- A discovered tool is WRITE-BEARING when its annotations say
  `readOnlyHint:false` or `destructiveHint:true` — the policy then hides/blocks
  it exactly like a core write tool (settled decision #8).
- `tools/call` dispatch: core impl first, else the module's
  `call(name, args, ctx)` with `ctx = { project, paths, config, arbiter, log }`
  (`paths` = the same `projectPaths(cfg)` map core tools use; `arbiter` a
  best-effort state helper bound to the loaded config; `log` writes to stderr).
  A throwing module handler → `isError: true` with the module path in the
  message; the process stays up.
- `--dump-core-tools` flag prints the core tools exactly as `tools/list`
  shapes them (golden-file regeneration).
- Core tool definitions and behaviour: untouched.

## Deviations / decisions

1. **Origin (a) proven at unit level** (settled decision #7 anticipated this):
   the server has no repo-root override env, so a full-process test of the
   adapters glob would require writing into the real repo's adapters tree.
   The discovery function itself is unit-tested against a scratch repoRoot
   (default filename + `idlefill.mcp_tools`-named file + shadowing + sort);
   the end-to-end stdio tests prove origin (b).
2. **Duplicate-name acceptance wording**: the issue's settled decision #3
   defines duplicates as an error WITHIN one origin, with (a) SHADOWING (b)
   across origins (stderr note, not fatal). The acceptance bullet "duplicate
   tool name across two origins fails" is read as the within-one-origin rule
   (two module files of the origin the env lists) — implemented and tested
   that way; cross-origin (a)/(b) collision follows the explicit shadow rule.
   A module re-declaring a CORE name is additionally a startup error.
3. **IDLEFILL_MCP_TOOLS entries may be directories** (scanned for the default
   module filename). This is what makes "remove the file → gone from the
   list" true while the env entry stays valid; a missing FILE path is still a
   startup failure per settled decision #4.
4. **Write-bearing discovered tools** are identified by their declared
   annotations (`readOnlyHint:false` / `destructiveHint:true`) — the only
   signal the server has about a module's tool; documented in README.
5. `register(api)` shape: not implemented (out of scope), noted in the
   registry header and README.
